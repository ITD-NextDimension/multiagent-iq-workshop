# Lab 05-1. Resource-Constrained Track: Deploy the Web App Only

> An alternative to [Lab 05](lab-05.md), about 15 minutes. **If you completed Lab 05, skip this one.**

## Story

The full Lab 05 creates AKS, ACR, a session pool, ACS Email, and monitoring for every participant.
Provisioning all of that at once across a classroom strains quota, cost, and patience — and if one
participant's AKS stalls waiting for a public IP, the whole session loses its rhythm.

Lab 05-1 splits the work differently: **the instructor pre-provisions and shares the heavy
resources, and each participant deploys only their own web front end.** You still walk through a
complete Container Apps release, an HTTPS ingress, and reverse-proxy wiring — but you never touch
AKS, never need `kubectl`, and never hold a model key or a Kubernetes secret.

## Architecture

```text
Your own Container App (the only resource this lab creates)
  |  nginx reverse-proxies /ask, /charts, /send-email
  v
Shared AKS: opc-agents API              <- instructor-maintained
  |
  +-> Azure OpenAI / Foundry
  +-> MCP + dataIQ: ontology queries
  +-> Azure Communication Services Email

Shared Container Apps environment + ACR + pull identity   <- instructor-maintained
```

Your app holds **no** model key, ACS connection string, or Kubernetes permission. It knows one
backend address; the shared services carry everything else.

## Shared Resources

All of these are created and maintained by the instructor before class. The actual values live in
the `workshop-web.env` file the instructor hands out:

| Resource | Purpose |
|---|---|
| Resource group | Holds the shared resources and every participant web app |
| Container Apps environment | Your web app is created inside it |
| Container registry (ACR) | Stores the instructor's pre-built web image |
| User-assigned managed identity | Holds `AcrPull`; your app uses it to pull the image |
| Agent API on AKS | The backend that nginx reverse-proxies to |

## Required Access

Before class the instructor grants a **lab service principal** the Contributor role on that
resource group and shares its client secret. You sign in with it, run no RBAC commands, and need
neither a personal Azure account nor Portal access.

> Scoping the grant to one resource group makes the subscription visible to the service principal
> while keeping its blast radius inside that group — participants cannot affect anything else.

## Lab Steps

1. Confirm the instructor's `workshop-web.env` sits in
   [code/cloud/scripts/](../../code/cloud/scripts), next to `deploy-web-only.sh`.

2. Choose your app name. It **must be unique per participant** — `initials-web` works well:

   - 3–32 characters
   - lowercase letters, digits, and hyphens only
   - starts with a letter, ends with a letter or digit

3. Preview first to see what the script would change, without deploying:

   ```bash
   cd /workspaces/*/code/cloud/scripts && bash deploy-web-only.sh <your-app-name> --preview
   ```

   > That is the absolute path inside Codespaces / a Dev Container, so it pastes
   > cleanly from any directory. Running locally, replace `/workspaces/*/` with your
   > own repository directory.

4. Deploy for real (1–2 minutes):

   ```bash
   cd /workspaces/*/code/cloud/scripts && bash deploy-web-only.sh <your-app-name>
   ```

   The script prompts for the service-principal secret with hidden input, then signs in, verifies
   the shared resources, deploys, and prints your HTTPS URL.

5. Open that URL and validate with two questions:

   - `Which projects does account ACC-001 fund?`
   - `What is the total budget by project status? Draw a bar chart.`

   Confirm three things: the text answer comes from the Agent API on shared AKS; the chart renders;
   and the browser address bar always shows **your** Container App, never the backend IP.

6. Inspect the resource boundary:

   ```bash
   az resource show -g <resource-group> -n <your-app-name> \
     --resource-type Microsoft.App/containerApps \
     --query "properties.template.scale" -o json
   ```

   > This uses the **core** `az resource show` rather than the more familiar
   > `az containerapp show`, which comes from the `containerapp` extension. That
   > extension cannot always be installed in the workshop container (installing an
   > extension needs pip from az's own interpreter). Both commands read the same ARM
   > resource and print the same thing.

   Expect `minReplicas: 0` and `maxReplicas: 1`. That ceiling is fixed in
   [code/cloud/web-only.bicep](../../code/cloud/web-only.bicep) and participants cannot raise it.

## Deployment Notes

- This lab creates **exactly one** Container App; every other resource is an `existing` reference.
  The script is safe to re-run — an existing app is updated in place from the Bicep declaration.
- The first page load takes tens of seconds. With `minReplicas=0` the app scales to zero when idle,
  so that delay is a cold start, not a failure.
- **Run no delete commands.** The shared resource group holds other participants' and the
  instructor's resources; the instructor cleans up by app name after the session.
- Your app pulls its image with a managed identity, not ACR admin credentials.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `找不到共享资源配置 workshop-web.env` | Config file is in the wrong place | Put it in `code/cloud/scripts/` and re-run |
| `workshop-web.env 里这些值还没填` | You have the template, not the real config | Ask the instructor for the filled-in file |
| `应用名 'xxx' 不合规` | Uppercase, underscore, or wrong length | Rename per step 2 |
| Sign-in fails | Secret pasted with stray whitespace, or SP not granted | Re-paste; if it persists, ask the instructor |
| Resource group not visible / 403 | Pre-class grant is incomplete | Contact the instructor; **do not switch to a personal account** |
| Name already exists | Collision with another participant | Pick a different app name and re-run |
| `共享资源不可用` | A shared service is down | **Do not edit the script**; ask the instructor to restore it |
| Very slow first load | `minReplicas=0` cold start | Wait a few tens of seconds and refresh |

## Takeaways

- Deploying only the web tier still exercises a full ACA release, HTTPS ingress, and proxy wiring
- Sharing the heavy resources sharply reduces classroom quota, cost, and waiting
- `minReplicas=0` / `maxReplicas=1` is this lab's explicit resource boundary
- Least privilege: the participant app carries no model key, no ACS secret, no Kubernetes access
